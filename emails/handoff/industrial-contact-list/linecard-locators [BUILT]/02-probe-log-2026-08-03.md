## 1. Rules honoured

- ≥3s per host, one worker per origin, every response cached under
  `data/raw/_cache/linecard-*/` — re-runs never re-hit origin.
- Honest desktop UA, never rotated. **Hard 403 = that target stops instantly**;
  429 = one exponential backoff ladder then leave it alone. No UA rotation, no
  host switching, no retry storms (`_polite.py`, ridden verbatim).
- Re-validation is part of the probe, not a preliminary (§5i: Matthews went
  200 → Cloudflare 403 inside one day). Yesterday's "reachable" is re-measured
  today before anything else is trusted.
- **robots.txt read first, per origin, RFC 9309 longest-match** (the
  `02-robots-posture-2026-08-03.md` method from E4, including its lesson that
  the serving host's robots file governs, not the www host's). **A data path
  Disallowed for the host that serves it does not get queried in this session.**
  The forward policy ("robots.txt is not an automatic exclusion" — Artur,
  2026-08-01) makes an override *available*, but per-site overrides are
  explicit, dated, founder-signed calls (Enerpac precedent, §7.1). Artur is
  offline; an unsigned gate is a NO. A gated path is recorded as
  GATE:HUMAN-pending with default NO, and the locator is measured only as far
  as robots permits.
- **Request budget, stated before the run:** ≤8 requests per target host
  (robots + locator page + terms page if linked + ≤2 JS bundles + ≤1 endpoint
  shape check + 1 probe query + slack for a second page of the same query),
  six targets ≈ ≤48 origin requests. Skim: 1 request to `unitedcentral.net`
  + ≤1 homepage GET per never-assessed manufacturer (~57 hosts, one request
  per host, no retries, 10-minute wall-clock box). Nothing here is billed;
  the cost is wall-clock only.
- **One query per locator. No sweeps, no grids, no pagination beyond the single
  result set the query returns** (exception: if the payload itself says it is
  paginated, one extra page fetch is allowed to establish page size, and that
  is what the per-host slack is for).
- **Nothing gets built this session.** Step 4's harvester builds are
  GATE:HUMAN per site and Artur is offline → default "do not build" applies
  regardless of how good the numbers are. This session produces measurements,
  decisions, gate questions and routing only.

## 2. The decision rule — committed before the first fetch

Verbatim from `01-prompt.md` step 3, with the interpretation bands fixed now so
"near" and "materially below" cannot be rationalised after the numbers exist:

1. **Website coverage at or near 67.6%** (Timken benchmark) **and** the network
   is plausibly a few hundred companies → **build-worthy**.
   *Fixed band: ≥55% counts as "at or near"* (AD's 57.0% was workable; the
   five-source union fill is 70.3%; Enerpac 82.7%).
2. **Materially below** → skip, record the number, close it.
   *Fixed band: <55%.* It feeds Segment W (8,156 rows nobody has worked) — the
   §5f mistake, paying to grow a backlog while long instead of short.
3. **No website field at all in the payload** → **dead**, regardless of how
   clean the locator is (Yaskawa shape: 0% website → domain-resolution queue).
4. **Carries an authorization tier or a per-record line card** → keep alive
   even at mediocre website coverage, because §5h's real test is a signal or
   copy asset we do not already have. Columbus McKinnon's "CM Authorized
   Rigging Centers" is the case in point. (This overrides rule 2, not rule 3's
   dead verdict — a tier with no domains still can't be seated without
   domain-resolution work, and that cost gets stated, not waved away.)

Network-size test for rule 1: distinct companies in the returned sample, chains
identified and discounted; if the payload is complete-network-in-one (Enerpac /
NORD shape), the total count is the answer. A complete network under ~25
distinct companies is recorded as small (Interroll/FlexLink shape) — still
cheap to take later if robots permits, but it cannot justify build effort on
its own.

Routing, fixed now: static survivors → harvester candidates on the

### 6c. Two caps found by measurement, not assumed

**Samson caps a result set at 24 rows** — five Utility queries returned exactly
24, and four other industries were still returning fresh companies at the last
anchor of the 12-city grid. **The first pass was therefore incomplete by
construction**, and an extension pass over the five affected industries × 24
interior/secondary anchors ran on top of it. **CMCO caps at 50**, which is why
its sweep half-steps the radius rather than trusting a single 150-mile circle.
A locator that returns a round number is clipping; treating that as "the
answer" is how a sweep silently under-reports.

### 6g. The thesis, generalized — and it cost zero network

now exhausted. **The generalization was sitting in the cache the whole time:**
S1c fetched **406 dealer line-card pages** on 2026-08-01 and they are still on
disk under `data/raw/_cache/serp_pages/`. Read backwards they are 406 supplier

separately, because the difference between them is the finding:

- **Vocabulary pass** (`brands_named_on_page`, already computed by S1c): 94

  bodies): **found nothing real.** Its only non-noise output was "stocking",
