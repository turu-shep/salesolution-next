---
name: ship
description: Run static checks, generate a reviewer checklist from plan outcomes, create a PR
---

Ship the current feature branch as a PR: $ARGUMENTS

## Process

### 1. Gather context
- Read `.claude/state.json` for the current issue ID, branch, and plan file
- Fetch the Linear issue description
- Read the plan file AND the spec file (`docs/specs/<issue-id>.md`) if it exists
- Run `git diff <base>...HEAD --stat` to get the list of changed files
- Run `git log <base>..HEAD --oneline` to get all commits on this branch

### 2. Policy pre-flight
Read `.claude/policies/*.md`. For each policy whose `triggers:` list includes `ship` and whose `files:` pattern matches any file in the diff:
- Run the policy's required checks (only the enforceable ones — see `.claude/rules/policies.md` for the real vocabulary)
- If `enforcement: block` and a check fails → STOP, surface the policy, require override
- If `enforcement: warn` and a check fails → show the warning, continue

### 3. Static checks against plan outcomes

**Honest framing:** This step does NOT verify behavior — it checks what's observable from the code and diff. Behavioral verification ("visitor can submit the audit form") is manual and goes in the reviewer checklist (step 4).

For each completed step (✅) in the plan, read its `Expected outcome` field and classify it:

| Outcome type | Can be auto-checked? | What to do |
|--------------|---------------------|------------|
| "File/function/type/export X exists" | Yes | Grep for it in the diff, report ✅ or ❌ |
| "Sanity doc type Y registered" | Yes | Grep `sanity/schemas/index.ts` AND `sanity/structure.ts` for it |
| "Route POST /x exists" | Yes | Grep the route file, confirm the handler is defined |
| "Import of library X is present" | Yes | Check `package.json` and imports |
| "User can do X" | No | Add to reviewer checklist as a manual check |
| "Behavior Y when Z" | No | Add to reviewer checklist |
| "Endpoint returns 200 for valid input" | No (requires running server) | Add to reviewer checklist |
| "Metric Z improves by W%" | No (requires production) | Note in PR; not verifiable pre-merge |

Produce two outputs:

**Auto-checks table:**
```
Step  Outcome                                  Auto-check
1     glossaryTerm gains `aliases` field       ✅ field present in schema + registered
2     New module lib/foo.ts exports foo        ✅ export found
```

**Reviewer checklist (for the PR body):**
```
- [ ] POST /api/lead returns 200 on valid payload (start dev server, curl test)
- [ ] New glossary page renders draft content in /studio preview
- [ ] Lead notification email actually sent (check Resend dashboard)
```

Every manual item becomes an unchecked box in the PR description.

**Standing Salesolution lines:** add these to the reviewer checklist when the diff matches:
- Diff touches customer-facing copy (`app/**/page.tsx`, hero/section components, metadata):
  ```
  - [ ] copy: humanizer pass done; kill-list respected; no cold jargon on ICP pages
  ```
- Diff seeds or edits Sanity content:
  ```
  - [ ] content: seeded as DRAFTS (not published); new terms queued via scripts/glossary-queue.mjs
  ```
- Diff adds/renames public routes:
  ```
  - [ ] seo: metadata + JSON-LD (lib/schema.ts) present; sitemap picks up the route
  ```

### 4. Spec acceptance check (same honest framing)
If `docs/specs/<issue-id>.md` exists, read its "Must-haves" checklist. For each must-have, decide whether it's auto-checkable (static code presence) or manual (behavioral). Report the auto-checkable ones with ✅/❌; put the manual ones in the reviewer checklist.

If any auto-checkable must-have is ❌, STOP and ask the user how to proceed. Don't ship a PR where a provable must-have is missing.

### 5. Quality checks
Ensure all changes are committed:
- `git status` — if dirty, ask whether to commit or stash

Run quality checks:
- `pnpm lint` (changed files clean)
- `npx tsc --noEmit` (pre-existing `lib/lead-form/*` Zod errors are the known baseline — anything new fails)
- `pnpm test`
- `pnpm build` for changes that touch pages/routes/config

If any check fails:
- Attempt to auto-fix (lint --fix, obvious type errors)
- If the fix reveals a gotcha, create a learning in `.claude/learnings/`
- If unfixable, report and ask whether to proceed anyway

### 6. Auto-generate the PR
Build the PR content from actual data:

**Title:** `[ISSUE-ID] <Linear issue title or short summary>`

**Body** (auto-generated):

```markdown
## Summary
<2-3 sentences derived from the spec context + Linear issue description + what the diff actually shows>

## Linear
Closes ISSUE-ID
Spec: [docs/specs/<issue-id>.md](link) (if exists)
Plan: [docs/plans/<issue-id>.md](link)

## Changes
<Auto-generated from `git diff <base>...HEAD --stat` — group by area:>
- **area/**: description of what changed (from commit messages)

## Static checks
<Auto-check table from step 3 — only the things that could be auto-verified>

## Reviewer checklist (manual)
<Everything from the plan outcomes and spec must-haves that could NOT be auto-checked — the human reviewer needs to verify these>
- [ ] <manual check 1>
- [ ] <manual check 2>

## Test results
- Lint: ✅/❌
- Types: ✅/❌ (lead-form baseline excepted)
- Tests: ✅/❌ (N passed, M failed)
- Build: ✅/❌

## Policies consulted
<List of policies that triggered, and whether each passed>

## Decisions logged on this branch
<Grep .claude/decisions.jsonl for entries matching ISSUE-ID, list one-liners>

## New learnings on this branch
<List files under .claude/learnings/ created during this work>
```

### 7. Determine base branch
Default to the repo's default branch — here that's `main` (`git symbolic-ref refs/remotes/origin/HEAD` to confirm). Accept `--base <branch>` override in $ARGUMENTS.

### 8. Create the PR
```bash
gh pr create --title "..." --body "..." --base <base>
```

If `gh` CLI is not installed, output the full PR content for manual creation.

### 9. Post-ship updates
- Report the PR URL
- Add a comment on the Linear issue: "PR created: <PR URL> — K manual checks for reviewer"
- Update `.claude/state.json`: set `prUrl`, update `lastActivityTimestamp`
- Update Linear issue status to "In Review"

### 10. Preview deploy URL (if applicable)
The site deploys via Vercel — pushing the branch produces a preview deploy. Note the expected preview URL in the Linear comment. Don't poll the deploy API.

### 11. Log the ship
Append to `.claude/decisions.jsonl`:
```json
{"ts":"...","issue":"SAL-123","type":"ship","pr":"<url>","auto_checks_passed":N,"manual_checks_count":M,"policies_triggered":["..."]}
```

## Batch mode

If invoked for multiple branches (`/ship sal-123-foo sal-124-bar`), run sequentially. Ship failures in one branch don't block the others. Report a table of PR URLs at the end.

## Important

- **Don't confuse auto-checks with verification.** Auto-checks confirm that files and exports exist. They do NOT confirm that anything works. The reviewer checklist is the real gate.
- **Don't mark a behavioral outcome as ✅.** If it requires running something, it's manual.
- **Never auto-merge.** Creating a PR is the end of this command's scope.
- **Don't ship with unsatisfied auto-checkable must-haves** without explicit override.
- **Never publish Sanity content as part of a ship.** Drafts stay drafts; publishing is manual in `/studio`.
