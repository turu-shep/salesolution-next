# V1 → V2.0 Implementation Guide

> This document explains every change from V1 to V2.0, the complete file/folder structure,
> and exactly how to build, deploy, and use the upgraded agent.

---

## What V2.0 adds over V1

| # | Feature | What it does | Why it matters |
|---|---------|-------------|----------------|
| 1 | **Persistent Codebase Memory** | Builds a knowledge graph on first run, uses git diff on subsequent runs to only re-analyze changed files | Drops weekly cycle from 3–5h to 30–60min |
| 2 | **Multi-Persona Descent** | Analyzes through 3 expert lenses (Architect, User, Adversary) instead of one generic voice | Eliminates LLM mood-dependent analysis skew |
| 3 | **Business Impact Scoring** | Every task gets a revenue/milestone impact rating, not just effort/priority | Output useful to founders and stakeholders, not just devs |
| 4 | **Documentation Drift Detection** | Cross-references docs against code, flags where they disagree | Catches the silent killer of mid-stage projects |

### `knowledge-graph.json` — Persistent Codebase Memory ★ NEW

| Property | Value |
|----------|-------|
| Created by | Agent (first descent) |
| Modified by | Agent (every descent and delta run) |
| Read by agent | Pre-flight of every session |
| Purpose | Avoids re-traversing unchanged code |

**This is the single biggest change in V2.0.** See `schemas/knowledge-graph.schema.json` for the full structure.

**Core concept:**
Every file in the project gets an entry with:
- Content hash (SHA-256 of file contents)
- Last analyzed date
- Deepest descent level reached
- Which module it belongs to
- What it imports (dependencies)
- What imports it (dependents)
- Scores on all 5 dimensions
- Flags from all 3 personas
- Whether it's on a milestone-critical path

**On subsequent sessions:**
1. Agent reads knowledge-graph.json
2. Agent runs `git diff --name-only [last_commit_hash]..HEAD` (or compares file hashes if not a git repo)
3. For each changed file: mark as "stale" in the graph
4. For each stale file: find all dependents in the graph, mark those as "stale" too
5. Only descend into stale files — everything else inherits prior scores
6. After descent: update hashes, scores, flags for analyzed files
7. Write updated knowledge-graph.json

**Size management:**
For a 300-file project, the knowledge graph is roughly 100–200KB of JSON. For a 1000-file project, roughly 500KB–1MB. This is well within Claude Code's context handling.

**Fallback if knowledge graph gets corrupted or too large:**
The agent can always fall back to a full re-traversal. The knowledge graph is an optimization, not a dependency. If `knowledge-graph.json` is missing or malformed, the agent treats it as a first run and rebuilds from scratch.

## How the Knowledge Graph Works (Detailed)

This is the most complex new feature. Here's the complete lifecycle:

### First Run (no knowledge graph exists)

```
1. Agent checks for .agent/knowledge-graph.json → not found
2. Agent performs FULL descent (same as V1, but slower because it's building the graph)
3. At EVERY file the agent reads during descent:
   a. Compute SHA-256 hash of file contents
   b. Parse imports/exports to build dependency map
   c. Record scores and flags from all 3 personas
   d. Record descent level reached
   e. Record module membership
   f. Write entry to in-memory graph
4. After descent completes: write knowledge-graph.json to disk
5. Record the current git commit hash in the graph metadata
```

### Subsequent Runs (knowledge graph exists)

```
1. Agent reads .agent/knowledge-graph.json
2. Agent determines what changed:
   
   IF project uses git:
     a. Read last_commit from knowledge graph
     b. Run: git diff --name-only [last_commit]..HEAD
     c. Changed files = git diff output
     d. Added files = files in diff that aren't in knowledge graph
     e. Deleted files = files in knowledge graph that no longer exist on disk
   
   IF project does not use git:
     a. Walk the file tree
     b. Compute hash of each file
     c. Compare against stored hashes
     d. Changed files = hash mismatch
     e. Added files = no entry in graph
     f. Deleted files = entry in graph but file missing

3. For each changed/added file:
   a. Find all dependents in knowledge graph (files that import this one)
   b. Mark those as "stale" too (they may be affected by the change)
   c. This is the "cascade" — one changed file can trigger re-analysis of its consumers

4. Analysis scope = changed files + stale dependents
   Everything else = inherited (scores, flags, persona assessments carry forward)

5. Run descent ONLY on the analysis scope
   - Use same persona protocol as full run
   - Same scoring, same flags

6. After descent:
   a. Update hashes for all re-analyzed files
   b. Update scores and flags
   c. Update last_commit to current HEAD
   d. Remove entries for deleted files
   e. Add entries for new files
   f. Write updated knowledge-graph.json
```

### Dependency Tracking

The agent builds the dependency map by parsing imports:

```
For JavaScript/TypeScript projects:
- Parse `import` and `require` statements
- Resolve relative paths to absolute
- Track: which files import this file (dependents), which files this file imports (dependencies)

For Python projects:
- Parse `import` and `from X import Y` statements
- Resolve module paths

For other languages:
- Best-effort parsing of import/include/require patterns
- If parsing fails, fall back to directory-level dependency assumptions
  (files in the same directory are assumed to be related)
```

### Graph Size Management

```
Target: knowledge graph stays under 2MB for projects up to 2000 files.

Each file entry is roughly 500 bytes–1KB of JSON.
- 100 files → ~50–100KB
- 500 files → ~250–500KB
- 2000 files → ~1–2MB

If the graph exceeds 2MB:
- Strip detailed flags from files scored 8+/10 (healthy files don't need flag history)
- Collapse persona_flags into a single flag count per persona
- Keep full detail only for files scored ≤ 7 or on milestone-critical paths
```

## How Multi-Persona Analysis Works (Detailed)

### The Three Personas

Each persona is a scoring lens with its own priorities, flag format, and weight.

#### The Architect
```
Identity: Senior software architect reviewing for long-term maintainability.

Asks at every level:
- Is responsibility clearly separated? (logic in /lib/, UI in /components/)
- Are dependencies flowing in the right direction? (no circular imports, no upward dependencies)
- Would a change here cascade to many other files? (high fan-out = fragility)
- Does this follow the project's own conventions? (from CLAUDE.md)
- Is this testable in isolation?
- Will this approach survive 10x scale?

Scoring weight by dimension:
- Code Quality: × 2.0
- Test Coverage: × 1.5
- Completeness: × 1.0
- Robustness: × 1.0
- Security: × 1.0

Flag prefix: [ARCH-NNN]
Flag examples:
- [ARCH-001] Business logic in component — booking price calculation in BookingForm.tsx should be in /lib/business-rules/
- [ARCH-002] Circular dependency — /lib/stripe/ imports from /components/booking/ which imports from /lib/stripe/
- [ARCH-003] God component — DashboardPage.tsx (650 lines) handles data fetching, state, layout, and business logic
```

#### The User
```
Identity: Product designer reviewing for end-user experience.

Asks at every level:
- What does a first-time user see here? Is it obvious what to do?
- What happens during loading? (spinner? skeleton? nothing?)
- What happens on error? (useful message? blank screen? console.error?)
- What happens when there's no data? (helpful empty state? invisible div?)
- Does the success feedback match the action's importance?
- Would this work on a phone? On a slow connection?
- Are labels, buttons, and messages written for the ICP, not for developers?

Scoring weight by dimension:
- Completeness: × 2.0
- Robustness: × 2.0
- Code Quality: × 0.5
- Test Coverage: × 0.5
- Security: × 1.0

Flag prefix: [USER-NNN]
Flag examples:
- [USER-001] No loading state — BookingForm shows nothing while payment processes
- [USER-002] Cryptic error — "Error: BOOKING_CONFLICT" shown to user instead of "This time slot was just booked by someone else"
- [USER-003] Dead end — empty dashboard for new user with no guidance on what to do next
```

#### The Adversary
```
Identity: Security engineer and chaos tester trying to break things.

Asks at every level:
- Can I access this without being logged in? (auth bypass)
- Can I access other users' data? (IDOR)
- Can I submit malformed data? (input validation)
- Can I manipulate prices or quantities client-side? (payment integrity)
- Can I trigger a race condition? (double booking, double charge)
- Does the error response leak internal information? (stack traces, DB schema)
- Can I spoof a webhook? (signature verification)
- Can I escalate my role? (customer accessing admin functions)

Scoring weight by dimension:
- Security: × 3.0
- Robustness: × 1.5
- Completeness: × 0.5
- Code Quality: × 0.5
- Test Coverage: × 1.0

Flag prefix: [ADV-NNN]
Flag examples:
- [ADV-001] Auth bypass — /api/bookings/create uses session cookie, not getUser()
- [ADV-002] IDOR — /api/bookings/[id] returns any booking without checking ownership
- [ADV-003] Price manipulation — booking amount calculated client-side, not verified server-side
```

### How Personas Run at Each Descent Level

At every level, the protocol is:

```
1. MAP (once — structural inventory, shared across personas)

2. ARCHITECT PASS
   - Read the map through the Architect lens
   - Generate [ARCH-NNN] flags
   - Propose score adjustments for Code Quality and Test Coverage

3. USER PASS
   - Read the map through the User lens
   - Generate [USER-NNN] flags
   - Propose score adjustments for Completeness and Robustness

4. ADVERSARY PASS
   - Read the map through the Adversary lens
   - Generate [ADV-NNN] flags
   - Propose score adjustments for Security

5. COMBINE
   - Base scores (from the map) + all persona adjustments = final scores
   - Any score adjusted downward by 2+ personas = cross-persona flag (auto-promote)
   - Descent decision uses the FINAL combined scores
```

### Cross-Persona Promotion

This is the mechanism that prevents any single lens from dominating:

```
Rule: If 2 out of 3 personas flag the same file, function, or finding:
→ That finding is auto-promoted to P1 minimum during judgment.

Rule: If all 3 personas flag the same item:
→ Auto-promoted to P0.

Example:
- [USER-001] BookingForm has no loading state during payment → UX problem
- [ADV-003] BookingForm allows double-click during payment → security/integrity problem
Both flag BookingForm's payment submission → cross-persona promotion → P1 minimum

If [ARCH-005] also flags BookingForm (business logic in component) → 3/3 → P0
```

## How Business Impact Scoring Works (Detailed)

### Impact Levels

| Level | Definition | Priority Cap | Example |
|-------|-----------|-------------|---------|
| **Revenue Blocking** | Core transaction cannot complete. Zero revenue possible. | P0 | Stripe intent creation fails silently |
| **Revenue Degrading** | Transaction can complete but conversion/trust is damaged. | P0–P1 | No confirmation email — user thinks it didn't work |
| **Milestone Blocking** | A specific milestone fails its blocker test. | P0 | Dashboard shows "undefined" — can't demo |
| **Milestone Degrading** | Milestone achievable but with visible quality issues. | P1 | Empty states are blank instead of helpful |
| **Operational Risk** | Works today but likely to fail under real conditions. | P1–P2 | No webhook idempotency — double charges at scale |
| **Technical Debt** | No current business impact. Compounds over time. | P2–P3 | Business logic in 5 components instead of /lib/ |
| **No Business Impact** | Code quality issue with no path to user or revenue effect. | P3 max | Inconsistent import ordering |

### How the Agent Determines Impact Level

During judgment, for each finding:

```
1. Does this finding touch the core transaction? (from PROJECT-CONTEXT §1)
   YES → Revenue Blocking or Revenue Degrading

2. Does this finding block a milestone's blocker test? (from PROJECT-CONTEXT §3)
   YES → Milestone Blocking

3. Does this finding degrade a milestone without blocking it?
   YES → Milestone Degrading

4. Could this finding cause failures under concurrent/real usage?
   YES → Operational Risk

5. Does this finding make future changes harder or riskier?
   YES → Technical Debt

6. None of the above?
   → No Business Impact → P3 maximum
```

### Revenue Estimation

When the impact level is Revenue Blocking or Revenue Degrading, the agent estimates:

```
## Revenue Impact Estimate

Based on PROJECT-CONTEXT:
- Transaction value: $[X]
- Current/projected weekly transactions: [N]
- Issue affects: [all transactions / subset — describe]

If Revenue Blocking:
- Every transaction is lost until fixed
- Weekly impact: $[X] × [N] = $[total]

If Revenue Degrading:
- Estimated conversion drop: [%] (agent's best estimate based on UX severity)
- Weekly impact: $[X] × [N] × [%] = $[total]

Caveat: These are estimates based on the agent's analysis of the code.
Actual impact depends on user behavior. Use for prioritization, not financial planning.
```

## How Documentation Drift Detection Works (Detailed)

### When It Runs

During the Ascent phase, after scores are rolled up but before the core transaction trace. This timing is important — the agent has already read all the code during descent, so it has full context to compare against documentation.

### What It Checks

The agent reads each document listed in the Drift Detection Scope (from analysis-params.md) and extracts **verifiable assertions** — statements that can be checked against the code.

```
Types of verifiable assertions:

1. NAMING CONVENTIONS
   Doc says: "PascalCase components, camelCase utilities"
   Check: scan all file names, function names, component names
   
2. STRUCTURAL CONVENTIONS
   Doc says: "API responses use { success, data, error }"
   Check: read all API route handlers, check return format

3. PATTERN REQUIREMENTS
   Doc says: "All API routes must verify auth via getUser()"
   Check: read all API routes, check for getUser() call

4. ARCHITECTURE ASSERTIONS
   Doc says: "/lib/stripe/ — Stripe integration logic"
   Check: is ALL Stripe logic in /lib/stripe/? Or is some in /app/api/?

5. WORKFLOW ASSERTIONS
   Doc says: "Bookings check availability via is_time_slot_available()"
   Check: trace all booking creation paths — do they all use this function?

6. FILE STRUCTURE ASSERTIONS
   Doc says: "Tests next to source: foo.ts → foo.test.ts"
   Check: for all tested files, is the test file adjacent?
```

### What It Does NOT Check

```
- Subjective assertions ("the codebase is well-organized")
- Future-tense assertions ("we will add rate limiting")
- External assertions ("deployed on Vercel") — agent can't verify infra
- Tool-specific assertions ("use /push-task to create issues") — agent can't verify CLI tools
```

### Severity Levels for Drift

```
HIGH — Assertion is about a safety or correctness pattern and code violates it
  Example: "All API routes must verify auth" but 3 routes don't

MEDIUM — Assertion is about a convention and code partially follows it
  Example: "API response format { success, data, error }" but 4/20 routes differ

LOW — Assertion is about style/preference and code mostly follows it
  Example: "Tests next to source" but 40% of test files are in a /tests/ directory

INFO — Doc describes something that doesn't exist yet or has changed
  Example: Module doc describes a feature that was removed
```

### Fix Direction

For each drift, the agent determines whether to fix the code or fix the doc:

```
Fix Code when:
- The doc describes a safety pattern (auth, validation) → code should comply
- The doc describes a convention the rest of the codebase follows → outliers should comply
- The assertion prevents bugs or confusion → code should comply

Fix Doc when:
- The code has evolved past the doc and the new pattern is better
- The doc describes something that was never implemented and isn't planned
- The doc is overly prescriptive about something that doesn't matter

Flag for Manual Decision when:
- Both code and doc have a valid point
- The right approach requires an architecture decision (→ ADR in V2.1)
```

This is where the investment pays off. Every run after the first is dramatically faster.

## Validation: How to Know V2.0 Is Working Correctly

### Check 1: Knowledge Graph Accuracy
After first run, spot-check 5 random files in knowledge-graph.json:
- Is the hash correct? (`shasum -a 256 [file]` should match)
- Are dependencies correct? (do the imports listed actually exist in the file?)
- Are scores reasonable? (compare against your own assessment of those files)

### Check 2: Persona Coverage
Open descent.md and check any module:
- Are there [ARCH-NNN], [USER-NNN], and [ADV-NNN] flags?
- Do the Architect flags focus on structure, not UX?
- Do the User flags focus on experience, not architecture?
- Do the Adversary flags focus on security, not code quality?
- If all three personas say the same generic thing, the persona separation has failed.

### Check 3: Delta Run Efficiency
After a delta run, check:
- How many files were re-analyzed vs. total files in the project?
- If you only changed 3 files, did the agent analyze ≤ 15 files (changed + dependents)?
- Did the agent explicitly note inherited scores for unchanged modules?
- If it re-analyzed the entire codebase, the delta mechanism failed.

### Check 4: Business Impact Scores
Open recommendations.md and check P0/P1 tasks:
- Does every task have a Business Impact level?
- Do Revenue Blocking/Degrading tasks reference the core transaction?
- Do Milestone Blocking tasks reference a specific milestone and its blocker test?
- If a P0 task has "Technical Debt" impact, the scoring is broken — TD should never be P0.

### Check 5: Drift Detection
Open drift-report.md:
- Does it list specific assertions from specific documents?
- For each drift: is the "Code Reality" column specific (file paths, counts)?
- Does each drift have a severity and fix direction?
- Cross-check 2–3 drifts manually — is the agent right about the mismatch?

## Troubleshooting

### "The knowledge graph is too large for Claude Code's context"
- Run the compaction protocol (§2.0.4 in AGENT.md): strip detail from healthy files
- If still too large: split analysis into module-level sessions instead of full-project

### "The delta run re-analyzed everything"
- Check if knowledge-graph.json has a valid last_commit hash
- Check if git history is intact (`git log --oneline -5`)
- If the project isn't using git, hash-based comparison runs slower — this is expected

### "All three personas are saying the same thing"
- Check analysis-params.md persona weights — they may all be set to 1.0
- The AGENT.md persona definitions need to be distinct enough that the LLM differentiates
- If this persists, the personas section in AGENT.md may need stronger role-playing instructions

### "Business impact scores feel arbitrary"
- Check if PROJECT-CONTEXT §4.5 (revenue context) was filled out
- Without transaction value and volume data, the agent can't estimate revenue impact
- Fill out the revenue context section and re-run judgment only

### "Drift detection missed obvious mismatches"
- Check if the document is listed in analysis-params.md drift scope
- Check if the document's assertions are verifiable (subjective or future-tense statements are skipped)
- If the document wasn't in PROJECT-CONTEXT §5.2, the agent doesn't know to check it
